# p115strmhelper V3 待决策问题

当前有 **4 项功能决策和 2 项外部支持范围**等待确认。D1、D2、D4 需要整体重构；D3 只有在要求保留严格查询入口的数据库加速时才需要重构。以下方案均未选定，确认前不继续局部修改

依据：MoviePilot V3 `ad4f8fbd64e274a105560f841dc7f34e18ee559e`；对照 V2 `1528176beacc0f9f8d8d9cbf1adf048b0da67b5c`。复现使用隔离配置、本地临时文件和模拟云端返回，没有执行真实云端写入、删除或账号切换

| 编号 | 功能 | 需要确认的决定 |
| --- | --- | --- |
| D1 | 整理接管 | 必须保留跨文件批量整理，还是交回宿主逐任务执行；是否允许扩展宿主 |
| D2 | 整理完成后的 STRM 生成与清理 | 由插件记录并协调重复事件，还是由宿主提供后处理扩展 |
| D3 | Open 文件查询加速 | 接受宿主实时严格查询，还是继续设计带云端确认的数据库加速 |
| D4 | 停止、重载、配置及账号切换 | 等待旧任务完成后切换，还是允许携带独立上下文的新旧任务并行 |
| E1 | 分享转存后的媒体信息上报 | 是否要求完整支持 V3 新增媒体来源，进而扩展服务端与 SDK 协议 |
| E2 | V3t 无 GIL 运行时 | 只支持标准 V3，还是另行推进依赖构建及无 GIL 并发适配 |

## D1 整理接管

**影响功能**：`pan_transfer_takeover` 开启后的批量移动／复制、重命名、关联字幕和音轨、预览、整理历史、失败重试及批次刮削

**问题**：插件入队即向宿主返回成功，之后自行批量操作和记录历史。V3 要求实际操作始终关联同一个持久任务，保存执行计划和进度，并统一提交最终状态。当前插件没有承接宿主的任务租约和执行检查点；重新构造任务或单独补写历史不能完成原任务。部分旧历史和重试接口也已移除，因此当前接管不能视为 V3 可用

需在同一方案中解决：

- 批量操作与每个宿主原任务的对应关系，避免宿主恢复任务时与插件重复操作
- 已移动文件但后续重命名、历史或通知失败时的恢复，以及主文件／关联文件部分成功的结果记录
- 识别、分组和预览使用 V3 媒体来源及 ID，并与实际执行计划保持一致
- 历史、完成事件、刮削和任务终态统一结算；未接管分支也保留原任务身份
- 使用宿主实际选中的存储对象，确保整理后更新的是正确实例的缓存

| 方案 | 收益 | 代价与影响 |
| --- | --- | --- |
| A：保留批量能力，建立持久批量协调机制 | 保留跨文件批量优化及关联处理目标 | 要记录逐任务／逐文件进度、部分成功和恢复结果；现有宿主扩展点可能不足，需要配套扩展 |
| B：交回宿主原生逐任务执行 | 由宿主统一计划、执行、恢复和结算，插件提供存储、命名及覆盖扩展 | 批量性能和关联文件处理不能假定原样保留，须先列出功能差异再决定 |

**需要确认**：跨文件批量整理是否是必须保留的能力；是否允许修改 MoviePilot 宿主扩展接口

**验收条件**：租约到期、进程重启、移动成功后后续失败、主／关联文件部分成功均可恢复；每个原任务只有一致的最终结果，历史和事件不会与实际文件状态脱节

**定位依据**：插件 [transfer_chain.py](../../plugins.v3/p115strmhelper/patch/transfer_chain.py)、[整理执行模块](../../plugins.v3/p115strmhelper/helper/transfer)、[任务模型](../../plugins.v3/p115strmhelper/schemas/transfer.py)；宿主 `app/chain/transfer/{execution,queue,plan,settlement}.py` 的任务准入、计划和结算流程

## D2 整理完成事件的重复处理

**影响功能**：整理完成后生成 STRM、下载字幕／音轨，以及 `latest` 模式下清理旧版本文件

**问题**：V3 持久事件采用至少一次投递。即使本插件已处理成功，其他监听器失败也可能使该事件再次投递。已复现：先处理旧结果 A，再处理新结果 B，随后重放 A，旧 A 的清理逻辑删除了较新的 B

事件 ID 只能辨认同一个事件，不能证明当前文件仍属于该事件。只做事件去重、按历史 ID 排序，或关闭原清理功能，都不能完整解决资源归属和部分失败后的恢复

| 方案 | 收益 | 代价与影响 |
| --- | --- | --- |
| A：插件持久后处理机制 | 在插件内记录事件进度、文件归属及已完成操作，保留生成和清理能力 | 需要确定新旧结果的可靠判断依据，以及文件操作与处理记录不同时成功时如何恢复 |
| B：宿主提供后处理扩展 | 由宿主提供资源版本、固定的任务输入和结果记录，插件据此执行 | 需要宿主配合设计接口，并明确宿主与插件各自的恢复责任 |

**需要确认**：后处理协调由插件承担，还是允许扩展宿主；原有生成／清理能力作为方案保留目标

**验收条件**：重复和乱序事件不覆盖或删除较新的有效结果；部分操作完成后重试不会重复产生错误副作用；其他监听器失败后的重投仍能正确处理

**定位依据**：插件 [helper/strm/transfer.py](../../plugins.v3/p115strmhelper/helper/strm/transfer.py)；宿主 `app/startup/composition/outbox.py` 的完成事件恢复和严格分发。问题可独立于 D1 发生，即使整理交回宿主，STRM 后处理仍须处理重放

## D3 Open 严格查询与数据库加速

**影响功能**：经宿主文件管理入口查询网盘文件时，原本优先使用插件本地数据库的加速路径；不代表所有存储增强失效

**问题**：V3 文件管理入口从 `get_item` 改为 `get_item_strict`，插件只增强了前者。严格方法在 V2 已存在，变化的是调用入口。当前 V3 因此走宿主实时查询，不再命中这条数据库加速路径

严格查询必须区分“确认存在”“确认不存在”和“无法确认”。旧增强可能直接返回数据库记录，或把查询异常变成 None；直接移植到严格入口会使宿主持久执行错误判断文件状态

| 方案 | 收益 | 代价与影响 |
| --- | --- | --- |
| A：接受宿主实时严格查询 | 保持 V3 的存在性判断，本项无需新增重构 | 该入口失去原数据库加速，可能增加请求和耗时 |
| B：设计带云端确认的增强查询 | 尝试保留数据库辅助能力，同时满足严格查询要求 | 需要明确缓存可用条件、回源确认及未知状态处理，收益须实测 |

**需要确认**：是否接受这条查询路径使用宿主实时查询；当前实现保持方案 A 的调用路径，但尚未把性能取舍视为用户已接受

**验收条件**：存在、不存在和网络异常三类结果明确区分；过期数据库记录不成为当前云端状态的证明；不破坏宿主持久任务的恢复判断

**定位依据**：插件 [patch/u115_open.py](../../plugins.v3/p115strmhelper/patch/u115_open.py)、[core/u115_open.py](../../plugins.v3/p115strmhelper/core/u115_open.py)；宿主 `app/modules/filemanager/module.py:get_file_item` 与 U115Pan 的 `get_item_strict`

## D4 停止、重载与配置／账号交接

**影响功能**：配置保存、扫码及账号切换、插件停止／重载，以及仍在执行或等待执行的 API、调度任务、事件、直接存储请求、302 线程和延迟清理；涉及客户端、下载器、路径、缓存、数据库及 FUSE 资源

**问题**：V3 依据插件的停止结果决定后续资源释放，只有显式 False 才保留未完成步骤。当前部分入口已能反馈停止状态，但仍有调用未被覆盖，不能把停止返回 True 当成所有旧工作均已结束

| 已复现或已确认的边界 | 影响 |
| --- | --- |
| Open 查询及八类上传／目录操作未结束，停止仍返回 True | 新配置发布后旧线程继续执行；旧递归目录结果实际写入当前缓存和重新打开的数据库 |
| 302 协程取消或连接池关闭时，底层线程、旧结果回写或延迟副本清理仍未结束 | 新旧 Redirect 对象交接后，旧操作仍可能继续产生副作用 |
| 同一插件对象保存配置后，V3 保留其旧的一次性任务 | 旧任务执行时使用新客户端、下载器和路径；待派发及已获宿主执行资格两种时点均已复现 |
| 宿主部分 stop／reload 入口使用 `require_quiesced=False` | 即使插件报告尚未停止，也不能单独阻止强制释放资源 |

上述复现保留实际宿主对象、线程、调度或本地数据库，云端出口均为替身。V2／V3 的同对象待执行任务处理有源码差异；已获执行资格的回调没有做 V2 同时点动态对照，不单独认定为 V3 新增缺陷

| 方案 | 收益 | 代价与影响 |
| --- | --- | --- |
| A：旧任务全部结束后切换 | 统一停止接收相关新工作，等待已受理任务结束，再发布新配置并释放旧资源 | 保存配置／切换账号可能等待；超时须保持旧配置和资源，并明确重试方式 |
| B：新旧任务携带独立上下文并行 | 每批任务固定使用所属账号、配置、客户端和路径，结束后释放对应资源 | 能减少切换等待，但需要维护多套资源和执行状态，设计与验证复杂度较高 |

两种方案都必须覆盖尚未进入插件的调度回调、直接补丁调用、不可取消线程和延迟清理，并明确配置保存失败及宿主强制重载时如何交接。FUSE 的挂载归属和就绪状态需纳入资源交接验证，不能仅按 Python 线程存活判断挂载状态

**需要确认**：切换时是否允许等待旧任务，还是要求新旧任务并行；是否允许为强制重载配套修改宿主

**验收条件**：旧任务始终使用正确的账号、路径和资源；不会在切换后向新账号的缓存／数据库写入旧结果；停止超时和保存失败不会提前释放旧任务仍需使用的资源；运行中重载及不可取消线程均有明确交接结果

**定位依据**：插件 [入口与配置保存](../../plugins.v3/p115strmhelper/__init__.py)、[服务生命周期](../../plugins.v3/p115strmhelper/service/__init__.py)、[一次性任务](../../plugins.v3/p115strmhelper/service/one_shot.py)、[Open 调用](../../plugins.v3/p115strmhelper/core/u115_open.py)、[302](../../plugins.v3/p115strmhelper/helper/r302/__init__.py)、[FUSE](../../plugins.v3/p115strmhelper/service/fuse/__init__.py)；宿主 `app/runtime/extensions/plugin/lifecycle.py` 与 `app/scheduler/oncejob.py`

V2 已存在的全局补丁覆盖、内存队列崩溃恢复和普通缓存问题，不单独作为本次 V3 重构依据

## E1 分享信息上报的媒体身份协议

**影响功能**：分享转存成功后按 `upload_share_info` 开关上报媒体信息，不是整个分享转存流程

**限制**：`p115center-sdk==0.0.17` 的 `ShareInfo` 仅有 TMDB、IMDb、TVDB、豆瓣、Bangumi 等固定编号字段，缺少通用 `media_id`、`anilist_id` 等字段。能发送 V3 来源名称，不等于能完整传输该来源的原生身份

**需要确认**：是否要求完整支持 V3 新增来源的上报。若要求支持，需服务端与 SDK 一起扩展；若暂不推进，应明确保留当前协议的表达范围。不能把其他来源的编号写入 TMDB 字段，也不自行关闭上报

**验收条件**：新增来源的来源名和原生 ID 能从插件经 SDK 完整传到服务端，并按正确身份保存和读取

**定位依据**：插件 [helper/share/__init__.py](../../plugins.v3/p115strmhelper/helper/share/__init__.py) 的 `post_share_info`，以及外部 SDK 的 `ShareInfo` 模型

## E2 V3t 无 GIL 运行时

**影响范围**：Python 3.14 无 GIL 运行时，不影响本项对标准 V3 支持范围的划分

**限制**：当前 `p115center-sdk` 及部分随包原生扩展缺少 `cp314t` 兼容构建，实际依赖解析无法完成。包索引当前为 `v3t=false`，不能通过放宽检查或删除功能依赖实现支持

**需要确认**：本次是否只支持标准 V3。若要求 V3t，需要先取得上游 SDK 兼容构建，再为其余原生扩展构建对应制品并验证无 GIL 并发行为

**验收条件**：目标运行时能够完整安装所有依赖，原生扩展实际加载成功，并通过无 GIL 环境下的并发测试

**定位依据**：[V3 依赖清单](../../plugins.v3/p115strmhelper/pyproject.toml)、[随包制品](../../plugins.v3/p115strmhelper/wheels)、[包索引](../../package.v3.json)
